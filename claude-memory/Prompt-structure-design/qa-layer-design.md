## 0. 总纲（一句话）
**贵的阅读只做一次、离线做、缓存起来；查询时靠检索把全库收口到短名单，只在需要时重读那几篇 PDF。**

> 推论：`summarize` 阶段"每篇一个子 agent 读 PDF"——**总结就是"读过这篇 PDF"的永久缓存**。每次查询重读全库 = 扔掉缓存重复付费。

## 1. 两种料的角色：地图 vs 实地
| 料 | 角色 | 用途 |
|---|---|---|
| 总结 + 合成层 + 引用图（中文、curated、离线攒）| **地图** | 检索底料、分诊、跨文章框架、给 agent 看路 |
| PDF（原文）| **实地** | 要精确数字/方法/边界时，按需深读取一手 |

纪律：地图都是"已读过的缓存 / 二手蒸馏"，**精确论断一律回 PDF 一手**（"数字让位 PDF"，与总结哲学一致）。

## 2. Consumer 与优先级
- **主用户 = 卡在自己项目里、临时来问的另一个 Opus agent（出口②）**；用户本人偶尔来（出口①）。
- **质量第一**：可以等、可以多读多核验；**但 token 仍靠检索 gate**（不为省钱牺牲质量，也不无脑读全库）。
- **诚实是硬约束**：没有就说"库里没有"，绝不编。

## 3. 问答主管道
```
问题
 ① 理解层      claude 把"工程问题语"→学术概念(展开缩写+中英双语+HyDE)   ✅已建(understand.py)
 ② 混合召回    FTS+向量 收口到一个【慷慨短名单】(质量优先,宁多勿漏)        ✅已建(search.hybrid)
 ③ 召回放大    顺引用图拉命中篇的邻居 + 合成层当第二索引(补漏)            🆕
 ④ 分诊        按总结挑 top-K(K随问题深浅/模式伸缩)                       🔧rerank 改
 ⑤ 出答案      ┌ 装得下 → Opus【直接读这K篇PDF】(保细节+跨文章推理)       🔧/🆕
              └ 装不下 → fan-out【每篇抽"带出处的原文证据"(非总结)】→单综合器  🆕
 ⑥ 核验        第二模型对着PDF复核每条论断(张冠李戴/方向反转)            🆕(复用 verify 哲学)
 ⑦ 交付        蒸馏答案 + 出处(DOI/PDF路径/质量标记/核查态) + 诚实标缺口   🔧answer 改
```

### 实证支撑（论文/对比/数字**全汇总在 `claude-memory/Prompt-structure-design/qa-layer-evidence.md`**，一处可查；下面只摘要）
- **⑤ 装得下时"直接读 > 先总结再汇总"**：压缩式普遍不如 full-context、迭代管道有"灾难性信息丢失"；层级总结**掉实体/数字**；分块独立处理**串味**（把一段论断安到另一段实体上 = **张冠李戴**，正是 verify 阶段最恨的错）。→ 装得下就让 Opus 一起直接读。
- **装不下才 fan-out，且"抽证据"不"写总结"**：Chain of Agents 证明超长内容拆开分读 > 单一大窗口（+最多10%，靠短上下文聚焦，避 lost-in-the-middle ~32K 起劣化）；但总结是掉数字/串味的元凶，抽原文片段+引用损失小。
- **fan-out 只用在独立的"读"，"合并"必须单线程+结构化+核验**：Anthropic 多 agent 在"广度优先独立探索"上+90.2%、但 15×token、且"需共享上下文/强依赖的场景不适合多 agent"；Cognition + MAST：无结构多 agent **放大错误 17×**、协调崩溃占失败 37%、有依赖任务过 ~4 agent 见顶 → 写入/综合单线程。
- **混合最优**：检索缩范围 + 长上下文一起综合，8 场景 7 胜单用任一种。

## 4. 来源不止"那几篇"（跨文章内容是一等公民）
- **合成知识层**：离线把跨论文的方法族/共识/**矛盾**蒸馏成主题笔记 → (a) 可直接答"X 有哪几种方法各自权衡"（stuck agent 零 PDF 拿到）；(b) 当综合器脚手架。雏形见 `tools/cross_topic.py`。
- **引用图**：补召回（③）。`citations` 表已有。
- **告诫**：合成层是二手、会过期 → 定期重蒸、**显式记矛盾别抹平**、精确论断仍回一手 PDF。

## 5. 三档查询（按问题深浅给不同料/成本）
| 档 | 例子 | 给什么 |
|---|---|---|
| 大意级 | "这领域有哪些路子" | 合成层笔记 / 总结，**不读 PDF** |
| 细节级（默认）| "XX 方法具体怎么做/数字" | 深读 top-K PDF（K≈3–5）|
| 穷尽级（显式 opt-in）| "一篇不漏列出所有做 X 的" | fan-out over 短名单/整主题 |

## 6. Agent 出口契约（`--json`）
机器可读 + 出处齐全 + **诚实哨兵**（无→"库里没有"）+ **可行动**（给 PDF 路径/指针，让它用自己项目上下文自己深究——它有我们没有的上下文）+ **蒸馏**（别倒原文撑爆它的 context）。理解层负责把它的工程问法翻成学术概念。

## 7. 投入分工（两条线解耦，避免互相绑架）
- **总结质量（核查）** 主要为"人读文摘 + 合成层 + 导出 ARS"兜底；
- **答案细节** 走 PDF。
- 不为"问答要准"去无止境抠总结数字；也不因"答案走 PDF"就觉得核查白做。

## 8. 检索的两种模式：小库 agentic / 大库索引（2026-06-19 用户拍板）
> 缘由：用户问"为什么不让 claude 直接进文件夹找、并发开 agent、token 又不是问题，中间加索引层不是加摩擦？"
> 讨论结论（见 SESSION 2026-06-18 第六段）：在当前规模（41 篇有总结）下用户直觉对——暴力全读召回 100%、更简单、少摩擦。索引层此刻价值不在召回，而在"地图能力 + 低延迟 + 能活到库长大"。所以**不是二选一，是按库大小分两套**。

| 模式 | 何时用 | 怎么做 | 索引(方案A)的角色 |
|---|---|---|---|
| **小库 agentic（现在默认）** | 库小到"地图"能近乎全看（当前 ~41 篇总结）| claude 当主脑自驱探索：读总结/合成层 → 顺引用图多跳 → 深读 PDF 终选 → 综合+核验。可近乎穷尽，召回靠"几乎全看"而非预筛 | **可选工具/加速**，不当闸；claude 想用就调，不想用就直接 fan-out 读 |
| **大库索引（以后库大了切）** | 库大到没法全读（latency/并发/蒸馏成本扛不住）| 先用 FTS+向量混合召回**预筛**成慷慨短名单 → 再 agentic 深读短名单 | **必须的闸**：不预筛就读不完 |

- **切换信号 = 库规模，临界落在「几百~1000 篇」（2026-06-19 算账修正,原写 2000 偏晚）**：1000 篇总结 ~3M token **塞不进一个 Opus(1M) 单上下文**→① 一个 agent 全读就崩了,必须 ③ 先筛(1000→~30-50)→ 再 ②/① 读。**到 ~1000 就该切大库模式,不是 2000。** 41 篇(现在)两轴容量都不触发(全总结~10-20万、连41篇PDF~60万都进1M),放心纯 agentic。
- **方案A 不删**：已建好（understand/search/index/rerank/answer），是大库模式的现成召回闸 + agentic 随手能调的工具（PaperQA2 式：agent 调检索工具,不闭眼全读）。"A 是 B 的零件,不浪费。"
- **⚠️ ②③ 是「按库大小交接的接力」,不是二选一比赛（2026-06-19 纠偏）**：实证看似打架(CoA:②>③;PaperQA2:③超人),其实**从没在同一库大小比过**——**读得完→用 ②(更强);读不完→只能 ③(仍超人)**,没有"明明能②却被迫用更差的③"的场景。**PaperQA2 的"超人"(85.2%>博士73.8%)是几百万篇、②不可能的区间拿的,不构成我们 41/1000 篇搭建的依据**(此前我拿它背书=过度推销,已退回)。
- **两个轴别混（2026-06-19 澄清）**：轴1=读(一个 agent 全读 vs fan-out 并发);轴2=合成(相关料能否进**一个 agent 单上下文**推理)。本文档"装得下/装不下"指**轴2**。41 篇两轴都几乎不触发,fan-out 此刻只为"读得干净"(注意力卫生)非"容量逼",小库增益有限(2026 实证:lost-in-middle 仍在但变弱,工具价值从"补容量"转"聚焦")。
- **合成知识层是「比 ③ 更聪明的索引」,不只是料源（2026-06-19 升格）**：跨论文蒸馏的方法族/共识/矛盾(第④节)。① 大意级问题它当场答(零 fan-out 零检索);② 细节级当**语义路由**(已推理过的目录,指"去哪簇钻",胜过 ③ 机械的词/向量相似)。**它=②的离线缓存版+③的语义升级版,才是让 agentic 活到库长大的关键**(库越大蒸馏越厚地图越全,与 ③"库越大筛越狠"逻辑相反)。代价:吃总结(41/221 料薄→排总结铺开后)、二手会过期(精确回 PDF/定期重蒸/矛盾别抹平)、维护成本未算(薄弱点#3)。
- **token 免费是这次提前 agentic 的最大理由**：原先把方案B往后排,主因之一是怕 agent 高频探索烧 token;用户拍板"token 不是问题"后这条顾虑消失。

## 跟现有代码的 delta
- **✅ 不动**：理解层、混合召回、总结/核查流水线（地基）。
- **🔧 改**：`retrieve/rerank.py` 从"打分+抽证据+12000截断"→**只打分挑 top-K**；`retrieve/answer.py` 从"读截断证据"→**装得下直接读 PDF / 装不下 fan-out 抽证据**，加核验趟。
- **🆕 加**：PDF 深读、size-adaptive 分流、引用图召回、合成知识层、穷尽模式开关、硬化 `--json` 契约、问答记忆（靠后）。

## 待定 / 薄弱点（落地前用户要再诊断）
1. **"装得下/装不下"阈值**：lost-in-the-middle 大概几万 token 起劣化，但 Opus 窗口很大——K 和"总量预算"卡哪要实测，别拍脑袋。
2. **召回率 = 质量天花板**：短名单多慷慨？引用图/合成层补召回到什么程度算够？漏一篇后面救不回。
3. **合成层维护成本**：多久重蒸、谁触发、跨 200 篇蒸一次多贵——没算账。
4. **查询分档**：大意/细节/穷尽——agent 显式标 vs 理解层自动判？误判代价？
5. **核验趟额度**：codex 配额已天天爆（见 `claude-memory/modules-modification/verify/STATE.md`）——每次问答加一趟核验扛不扛？要不要只对高风险/低置信触发。
6. **料还薄**：整套假设"总结丰富"，但当前 221 篇仅 ~41 篇有总结——框架可先定，落地等总结铺开。

## 9. 架构主干：金字塔（2026-06-19 用户拍板收口）
> 缘由：用户问"④全读现在能用，但会长到不止 100 篇、后面还有蒸馏层（⑤），该怎么搭才不推倒重建？"
> 讨论见 SESSION `claude-memory/modules-modification/retrieve/STATE.md`（第九段）。**这一节是把 §3 主管道 + §4 跨文章料 + §8 两模式收口成一张主干图**——§4/§8 讲的"为什么做合成层/金字塔"是这节的前因，**别删，互为表里**。

**一句话**：贵的"读"在**建库时做一次、缓存成层**（总结=每篇缓存、合成层⑤=跨篇缓存），**查询时只读缓存层、为精确才下钻 PDF**。两条约束逼出这个唯一解：

- **约束1（会长到不止 100 篇）**：查询时全读成本 ∝ N，几百篇就超窗 + 合并区炸 → 活不过增长蓝图。金字塔查询成本 ≈ **恒定**（查薄薄一层蒸馏 + 下钻几篇），贵阅读转移到 build 时、只做一次。落点 = evidence §7"**总结=已缓存的 fan-out**"。
- **约束2（框架后面有蒸馏层⑤）**：⑤ 不是附加件，它就是"把贵的 fan-out 缓存成地图"的成品（=§4 合成知识层、§8"比③更聪明的索引"）。

```
        问答
         │  大意级 → 合成层⑤当场答（零检索零下钻）
   ⑤ 合成层(跨篇蒸馏/语义路由：去哪簇钻)   ← build 时 fan-out 一次性蒸出
         │  细节级 → 路由到相关簇
   总结(每篇缓存的分诊层)                  ← 已有
         │  要数字/精确 → 下钻
   原文 PDF(实地)                          ← 只读 survivors(~几篇)，装得下一个 Opus 直接读
```

- **④ fan-out 全读的两个正当岗位**（不废、但不是查询默认）：(a) **建⑤的工序**——离线、一次、并发安全（无 per-query 合并压力）；用户原话"总结+原文一起、小 agent 并发处理"放这里**正确**（蒸馏本就要地图+实地一起看）。(b) **`exhaustive` 兜底模式**——专给"一篇不漏"的穷尽查询，over 一个 topic 抽证据。
- **合并永远单线程**（MAST 17×）；金字塔查询只下钻几篇 → 合并区天然小，躲开全读的合并爆炸。
- **⑤ 增量更新是领域真空（evidence §7.6）**——我们自己啃：①**按簇蒸、按簇更新**（新论文落哪簇只重蒸那簇，不全量）；②**矛盾显式存别抹平**；③精确论断永远回一手 PDF（⑤是二手地图、会过期）；④攒够 N 篇整簇重蒸纠漂移。

**落地次序（贴"总结正在重做"现实）**：
1. **现在（总结薄）**：⑤ 先别建；查询走**临时路 = ④全读**（总结塞 context / fan-out 抽证据 → 单线程合）——**这就是先实现的那个、也是能用的**。
2. **总结铺开（≈100 篇）**：按 topic fan-out 蒸出⑤，⑤ 转正成导航层。
3. **几百+**：② index 升召回闸（替总结全扫做粗筛），⑤ 接管语义路由，增量按簇重蒸。
- 每档都复用前档产物，**没有"长大推倒重建"**。④ 现在搭的契约层（answer.py）/模式分发（ask.py）②③⑤ 全共用。
